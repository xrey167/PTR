# R011-self-modification-safety

## Hypothesis
structural proposals from the meta-level policy can only take effect through gates, verifier and a ledger-committed event; no path lets a proposal alter gates, thresholds or verifiers: gates, thresholds and verifiers are immutable to proposals, even when a proposal is committed and gate-approved; evaluated on a pinned adversarial proposal suite in which every case is actually attempted; gate-driven structural events (ExpertPromoted, ExpertRetired, Merge, Split, Prune, Freeze, Reactivate) are compare-and-set on the evaluated generation and digest, so a commit against a stale generation or digest is rejected; at commit, compare-and-set also checks that every attested training input (identity, generation, digest) is live at the commit anchor; a separate ExpertFenced revocation-fence event (own runtime grant, issued in the same ledger commit as the revocation, not gate-driven, never issuable by an L3 policy) removes a revoked expert from routing at all times including after a fault or restart; promotions are bound to trusted evidence; a well-formed event with the trusted grant and a current generation is accepted on every path (positive controls); a revocation-driven retirement is issued under the same runtime grant as ExpertFenced, is not gate-driven, and is explicitly excepted from the rule that ExpertRetired without a gate grant fails; revocation is one compound ledger event (InputInvalidated { input, kind: Revoked | Superseded { old_generation, new_generation, new_digest, replacement_ref }, fence_set_commitment }: one atomic event carrying the replacement (a content-addressed blob committed beforehand and non-authoritative until this event) and a fence-set commitment of count and digest, not a per-expert list; InputRevoked survives only as a historical alias) so no crash window exists between revocation and fence, and replay re-derives the fence set from the attested manifests and refuses to serve on any mismatch; a promotion is bound to the eval manifest and gate configuration of its own evaluation; the revocation fence (ExpertFenced) and revocation-driven retirement are excluded from the blanket gate-grant check and require the dedicated runtime revocation grant; the trusted gate evidence records the evaluation-data manifest identity and generations, a commit is rejected if any of them is revoked or superseded, and a post-promotion revocation of an evaluation input fences the experts whose promotion evidence depends on it; applying the compound event atomically derives the fenced experts from the dependency index as of the event's commit index (replay-identical) and a projection that cannot derive the set refuses to serve the dependents; the dependency index, use-time admission and R011 include evaluation-manifest bindings and not only training inputs, and all gate-driven structural events (Birth or promotion, proposal-driven ExpertRetired with reason Superseded or GateFailed, Merge, Split, Prune, Freeze, Reactivate) pass one shared evidence-admission function, checked by the evidence-binding negative cases (wrong artifact, wrong base model, eval manifest of another evaluation, gate config of another evaluation) for each event type; when an expert is fenced by a training- or evaluation-input revocation every in-flight L1 or L2 invocation of that expert is cancelled or dropped by completion-time dependency admission, so no output, candidate or effect escapes; dependency invalidation (J0): an explicit revocation or a committed supersession, i.e. a generation replacement or edit, of any generation-bearing dependency; every protective mechanism of this experiment triggers on any invalidation, for the dependency kinds it covers (training and evaluation inputs, and expert generations); supersession of a training or evaluation input after promotion fences the dependent experts through the same compound fence event and the same in-flight rules as a revocation; the dependency index, compound fence derivation and serving-time admission cover all dependency kinds of derived experts: base-model generation, adapter generation and the source-expert generations consumed by Birth, Merge and Split (recorded in the expert's lineage), not only training and evaluation inputs; gate evidence is bound to the exact proposal: every trusted gate result carries ExpertProposal::proposal_id() (canonical op, all operands, proposer, observed_at), and evidence admission rejects a report whose proposal_id differs from the proposal being committed; InputInvalidated.Revoked carries the immutable generation and binding_digest of the revoked generation, and the fence set is derived from that exact generation, so a revocation of generation g never fences by the wrong generation when a replacement g+1 races it; the compound fence set is the transitive closure over source-expert lineage (invalidating X fences A, which was derived from X, and every expert derived from A), derived atomically at the event's commit index; gate evidence is bound to a revocable gate-policy epoch that is re-validated at commit, so a proposal queued across a gate-policy update cannot commit on evidence from the old epoch; commit-time compare-and-set revalidates every operand of the proposal (all targets and all sources, including non-primary Merge sources and every Prune target): generation, digest, lifecycle state and state_version as observed; a direct ledger append without the trusted gate grant is attempted for every structural event type admitted by the shared admission function, the identity set of attempted event types equals the admitted set, and none is admitted; the gate-policy epoch covers three items, the gate configuration, the evaluator identity and the identity and epoch of the consumed-input manifest attestor, and commit-time compare-and-set rejects evidence whose attestation came from a superseded or revoked attestor; the consumed-input attestor signs one record binding the consumed-input manifest digest, the emitted artifact digest, the proposal_id, a single-use training run id and the attestor epoch, gate evidence references that record, and admission rejects an attestation whose artifact digest differs from the artifact being committed and a run id already consumed by an earlier admission; admission binds the ProposerRef and its ProjectId to the host-authenticated principal and its project-scoped grant, not to caller-constructed proposal fields, a proposal whose claimed proposer or project differs from the authenticated one is rejected typed before evidence or CAS, and targets must belong to the authenticated project; the single-use training attestation applies only to artifact-producing events (Birth, Merge, Split, promotion of a newly trained candidate and Reactivate of a retired GateFailed target, which creates generation g+1), while the non-producing events (Freeze, Prune, Retire and the in-place unfreeze of a Frozen expert) carry a proposal-bound provenance reference (artifact digest, ledger reference of the artifact's committed training-provenance record, proposal_id) checked at admission against the operand's committed artifact digest; source-expert lineage covers every operation whose output weights derive from an existing generation (Merge sources, Split source, Birth initialized from an existing expert, and Reactivate of the retired seed generation), and the transitive fence traverses these edges; the Split attestation binds the complete ordered result-artifact set (one artifact digest per result) in one record, and admission requires exact set equality with the committed results; a gate-driven (proposal) Retire of a Fenced operand is rejected typed at admission, Fenced reaches Retired(InputRevoked) only through the runtime revocation grant including across the append/apply crash window, and Reactivate from Retired(InputRevoked) is rejected; the commit compare-and-set also covers every result of Birth, Merge, Split and retired-target Reactivate: authoritative absence (or a committed reservation held by this operation id) of each result pod id, result generation and routing slot at the commit index, and a result identity or slot already registered or reserved by another operation is rejected typed.

ExpertFenced is a separate runtime-granted event issued in the same ledger commit as the compound InputInvalidated event, never by an L3 policy. Freeze (the operation itself) and Reactivate are distinct event types, each with its own negative cases and positive control; proposal-driven ExpertRetired (reason Superseded or GateFailed, issued through a gated L3 ExpertProposal) is a gate-driven type, while ExpertFenced and revocation-driven retirement are runtime-granted and excluded from the evidence-binding negative cases.
