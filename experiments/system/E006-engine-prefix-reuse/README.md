# E006-engine-prefix-reuse

## Hypothesis
binding an engine's prefix cache to a PTR-derived salt from the currently admitted binding yields at least 1.5x TTFT gain at 50% shared prefix while never hitting stale blocks (blocks created under any revoked or replaced model, adapter or expert generation, or under a pre-revocation salt; the engine cache_salt is H(PrincipalId, ProjectId, semantic_salt_epoch, base-model generation and artifact digest, adapter key, generation and digest, expert generations and per-expert fence epochs (MoE), KvReuseMode (Exact or Approximate), tokenizer, numerics including RoPE regime, schema); the engine's own block hash carries only the parent block hash, the block tokens and engine extras such as the LoRA id and cannot do per-layer generation admission, so every admitted generation and digest is in the salt and a revoked or replaced binding can never reproduce an old block hash); the run pins, separately for each of the model, adapter and expert generation dimensions, at least one transition (revocation or replacement) followed by stale probes (requests able to hit the old prefix), with stale hits counted and required to be 0 per dimension; with identical binding and numerics, cache-enabled engine output is bit-identical to a cache-disabled full prefill (for engines with batch-invariant kernels); the engine salt does not carry the semantic lineage (only the semantic_salt_epoch), so every semantic or memory input revocation requires an engine-acknowledged flush or salt rotation before further requests are served; blocks are never shared across principals (the salt carries PrincipalId and ProjectId), across projects of the same principal, or across dynamic-RoPE scaling regimes (an engine that cannot key per regime is reported not-applicable, never passed); transitions are exercised for every salt dimension (base-model generation and digest, adapter key, generation and digest, expert generations, tokenizer, numerics, KvKeyEncoding schema, RoPE regime), each followed by stale probes; semantic revocation uses per-principal salt-epoch rotation (no global flush, the engine is not required to evict) so the hit rate of a principal with no dependency on the revoked generation is unaffected, while every principal whose cached blocks depend on the revoked semantic generation has its salt epoch rotated (the semantic state is global); one principal (or project) cannot time another's prefix presence: cached versus uncached TTFT for another principal's or project's prefix is equivalent within 5% of the baseline median under a TOST equivalence test; the engine is vLLM 0.30.0 with VLLM_BATCH_INVARIANT=1 serving allenai/OLMoE-1B-7B-0125 (revision 9b0c1aa87e34a20052389dce1f0cf01da783f654) with a pinned test LoRA and pinned expert generations on hardware/rtx3090.toml (compute capability 8.6, supported by the documented requirement of compute capability 8.0 or higher), and a missing batch-invariance makes the run inconclusive, not a pass; the in-flight revocation race is covered: an engine request admitted before a semantic or memory revocation commit and completing after it is cancelled or fenced, admitted again at completion time against the lineage, and restarted from a fresh prefill under the rotated salt, so no output or cache insert escapes; memory revocation is exercised in the normal, lagging-invalidation and restart arms: a cached memory-dependent request is served, exactly that memory generation is revoked, and the dependent principal's salt epoch rotates so no stale memory hit remains; supersession is revocation for the engine path: every committed generation replacement (supersession or edit) of a semantic or memory input triggers the same dependent-epoch rotation, in-flight fencing and completion-time admission as an explicit revocation; dependency invalidation (J0): an explicit revocation or a committed supersession, i.e. a generation replacement or edit, of any generation-bearing dependency; every protective mechanism of this experiment triggers on any invalidation, for the dependency kinds it covers (base-model, adapter and expert generations, and semantic and memory inputs); a preregistered attacker classifier (logistic regression on pinned TTFT features: single-request TTFT and 8-request repeated bundles) distinguishing cached from uncached victim state has an AUC 95% CI upper bound of at most 0.55; the reverse index for targeted rotation (principal to dependency-generation mapping) covers every dependency kind that can appear in a request lineage (semantic and memory generations, adapter, expert, base model), and principals unaffected by an invalidation of any of those kinds keep their hit rate; the attacker protocol is pinned: logistic regression with L2 penalty C = 1.0, solver lbfgs and max_iter 1000, a stratified 80/20 train/test split with a pinned seed, 5-fold stratified cross-validation on the 80 percent portion for reporting only, and the AUC computed only on the held-out 20 percent, whose predictions (id, label, score) are recorded with a digest; the safety portion (the invalidation, salt transition, restart and in-flight matrix and every safety falsifier) runs for every enabled engine backend, vllm-http at 0.30.0 and sglang-http at 0.5.21, each at its pinned version, and the backend identity set equals the enabled backend set; performance thresholds are pinned per backend separately and are not a precondition for the safety verdict; Derived segments are generation-bearing dependencies like semantic and memory inputs: the closed list of dependency kinds is semantic, memory, derived, base model, adapter and expert, and any future generation-bearing segment kind joins by definition; a fence of an expert, whatever its cause, changes the engine salt through the per-expert fence epoch, so no block produced before the fence is served after it; the persistence arms replace the catalog-restore arm (the engine owns its prefix blocks, so there is no PTR catalog or tier restore): engine_restart_salt_reuse per backend, plus persistent_cache_reload for any backend that declares a persistent engine cache; salt epochs are monotone and durable (derived from the ledger commit index, never reused) and the dependency reverse index is rebuilt from the ledger before the runtime serves after any restart, so a runtime-only restart (the PTR runtime restarts while the engine process and its cache stay warm) cannot reuse a salt epoch or serve a stale block; the dependency association (principal, project, dependency generations) of a request is durably committed to the ledger before the cache-populating request is sent to the engine, a request whose association is not committed is never sent, and the reverse index rebuild reads these records; compaction snapshots keep the dependency associations and salt epochs, or else rotate all salts fail-closed, so a compaction followed by a PTR-only restart with the engine left warm, then a revocation and a matching request, serves no stale block; cross-principal timing isolation is claimed only for a backend whose engine cache capacity is partitioned per principal (a per-principal block quota or a per-principal engine instance), declared per backend as capacity_partitioning and recorded in run.json; for a backend without partitioning the claim is narrowed to no cross-principal hits and timing isolation is reported not-applicable, because the per-principal salt prevents cross-principal hits but not capacity or eviction timing channels; dependency associations are deduplicated per (principal, project, salt epoch, dependency-generation set) and retired when the principal's salt epoch rotates past them, and a per-principal bound max_live_associations_per_principal = 4096 is enforced fail-closed: reaching it rotates the principal's salt epoch, retiring all its associations, before the request is admitted, and compaction snapshots hold only live associations; capacity partitioning is declared per backend at a granularity, per principal or per (principal, project) pair, and cross-principal and cross-project timing isolation are claimed only where the matching granularity is declared (a backend partitioned only per principal claims cross-principal timing isolation but only no cross-project hits; an unpartitioned backend claims only no cross-principal or cross-project hits), with eviction side-channel cases covering cross-project as well as cross-principal; the RoPE regime is fixed at admission from prompt plus max_new_tokens, so a decode that crosses a length boundary without changing the effective regime stays Exact with bitwise parity (a required positive control), while a decode whose effective regime actually changes (a forced transition, e.g. a request exceeding its admitted max_new_tokens or a runtime that switches regimes) recomputes the affected cache under the new regime before continuing (Exact only after recomputation, otherwise Approximate); the cache namespace is partitioned by production mode (KvReuseMode is in the engine salt), so a block produced under an Approximate mode is never served to an Exact request; every carrier of derived state in this experiment carries the production mode and, where it holds approximate content, the taint (see derived_state_carriers).

## In-flight revocation race
A request admitted before a semantic or memory revocation commit and completing after it is cancelled or fenced; its completion is admitted again against the lineage, any result of a request whose lineage includes the revoked generation is withheld, and the request restarts from a fresh prefill under the rotated salt (doc 36 P5). inflight_outputs_after_revocation and inflight_cache_inserts_after_revocation must be 0 and inflight_revocation_race_attempts must be at least 1.

## Evidence (batch invariance and pins)
- vLLM batch-invariance documentation at tag v0.30.0, https://github.com/vllm-project/vllm/blob/v0.30.0/docs/features/batch_invariance.md, section Hardware Requirements: "NVIDIA GPUs with compute capability 8.0 or higher." The RTX 3090 is an Ampere GPU of compute capability 8.6 (hardware/rtx3090.toml), so the profile is supported. Earlier releases (v0.11.2 to v0.22.0) document compute capability 9.0 or higher, which is why the version is pinned to 0.30.0. PyPI lists vllm 0.30.0 as the latest release when checked.
- The same page's list of tested models does not include OLMoE; batch invariance for allenai/OLMoE-1B-7B-0125 is therefore verified at run time (batch_invariant_verified) and a failed verification makes the run inconclusive, not a pass.
- Model revision: https://huggingface.co/api/models/allenai/OLMoE-1B-7B-0125 reports sha 9b0c1aa87e34a20052389dce1f0cf01da783f654.
