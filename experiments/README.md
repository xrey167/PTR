# PTR Experiments

Every experiment has an ID, hypothesis, baseline, seeds, metrics, falsification criterion and immutable result directory. `experiments/registry.toml` registers each ID once, in one directory: `run_experiment.py validate` and the research gate refuse an ID registered twice, which the gate would check in one place and the runner could launch in neither.

Categories:
- `model/`
- `semdb/`
- `runtime/`
- `lifecycle/`
- `retrieval/`
- `feedback/`
- `system/`

Do not silently rewrite failed results. Supersede them with a new experiment/version and record the decision in `research/decisions/`.

## Preregistration

An experiment listed in `preregistration.toml` leaves `planned` only with a frozen preregistration. Once its status is `prepared`, `running`, `completed` or `failed`, `scripts/check_research_gates.py` fails CI unless:

- its manifest names its `entrypoint`, since the manifest is frozen from the first commit past `planned` and one named later could never be named, and the runner can build its command: it splits as a command, and each placeholder in it but `<seed>` is a key of the `[preregistration]` table holding an integer, a string or a boolean, the value the runner fills it with, since a freeze no run can use cannot be repaired;
- its `config.toml` holds a `[preregistration]` table with every key the list requires, each a pinned value of its declared type (`int`, `str`, `bool`, a non-empty `int-list` or `str-list`, or `file`), and no other key of the table holds a placeholder either;
- every value of that table is a boolean, an integer of magnitude at most 2^53 − 1, a string of printable ASCII or a list of only such integers or only such strings, and every key is printable ASCII, so that its canonical text has one spelling whoever writes it; `experiment.toml`'s `preregistration_sha256` is the SHA-256 of that text;
- a `file` key names a file in the repository, and the table's `<key>_sha256` is the SHA-256 of that file (`preregistered_bytes_digest`: in a text file, UTF-8 with no NUL byte, CRLF is read as LF, so a checkout that converts line endings holds the same digest; any other file is digested byte for byte, since its carriage returns are content), so the file's content is frozen with the table, not only its path. Since that digest holds the content alone, the file is not executable (mode `100644`, in the index and in every commit), as the executable bit changes what a command does with it, and as text it is committed with LF line endings, so no two committed versions that a command would read apart share a digest;
- the table's `seeds`, which every entry of the list must require as an `int-list`, names the manifest's seeds, integer for integer, each once, so no seed can be added after an outcome is seen and none counts twice in an aggregate;
- every baseline the list names is pinned at each key the list names for it, its status is pinned and not `blocked-*`, and the table's `baseline_<name>_sha256` is the digest of every file in the baseline's directory: the canonical text of the table mapping each file's path within the directory to its git mode and its SHA-256 (read as a `file` key's is), written `<mode> <sha256>` (`100644`, or `100755` for an executable file), over the files git tracks or would track there, so every setting of the baseline, not only the keys that must be pinned, and the implementation beside its configuration, down to which of its files are executable, are frozen with the table. The directory holds no file its `.gitignore` files ignore, such as a `__pycache__` entry, which an interpreter could run in place of a tracked file and git does not hold, and every file in it is named as a repository path (below), a name that is not UTF-8 being none; a commit whose baseline directory held another, such as `helper[old].py`, could not launch the experiment and froze nothing, whether or not its table named a digest of the baseline, so renaming the file is a repair, not a rewrite;
- `experiment.toml`'s `preregistration_rules_sha256` is the SHA-256 of the canonical text of the experiment's entry in `preregistration.toml`, so its types and baselines are frozen with the table;
- every run record (`run-*.json`, whose manifest `run_experiment.py` records) and aggregate (`run.json`) the experiment has committed in a results directory it has had (`results`, or a `results_dir` a committed manifest named) in any directory the registry has given it, whatever its `results_dir` is now, and those in its results directory (a file of that name elsewhere, such as a test's fixture, is none), name those two digests and the commit they ran at (`git_sha`), and that commit is on HEAD's history, where the registry placed the experiment in the directory it places it in now, and holds the same `[preregistration]` table, manifest digests, list entry, files and baselines; a run record also names the SHA-256 of `experiment.toml` at that commit (`manifest_sha256`) and has held the same content in every commit on every side of every merge since it was committed, an aggregate, which an aggregator may write again, holds to this in every version it was committed in, each version a regular file, each once committed is at HEAD where it was committed (one deleted and put back as it was, as a revert of its revert puts it back, is the record committed: while it is missing the gate fails and the runner launches nothing), no two run records are of one seed but for a command that failed to launch, since a seed run again after its outcome was seen could keep whichever run came out best, and the run records all name one program, one Rust toolchain and one environment (`executable`, `toolchain`, `environment`), which lie outside the commit and a replacement between seeds would leave unnamed (a program the command starts by name is found through the environment's `PATH`), and ran one tree: the repository at each run's commit is the first run's but for the seed records (`run-*.json`) of the results directory, since the command may run or read any file of it, an aggregate (`run.json`, `metrics.json`) or mutation evidence (`mutations.json`) committed between seeds included, which the tools write once the seeds have run (a script under `scripts/` changed and committed between seeds would leave records naming commits of different code; `listed_record_paths`, which a listed experiment's aggregator passes to `source_revision` too), and each is a regular file reached through no symlink. A preregistration rewritten after its runs thus fails even when the manifest and the records are rewritten to match, short of rewriting history. An aggregator of a listed experiment writes `preregistration_sha256`, `preregistration_rules_sha256` and `git_sha` into `run.json`;
- the manifest and `config.toml` at every such commit are the ones now, value for value and of one type (`1`, `1.0` and `true` are three values, and so are `0.0` and `-0.0`, and `nan` and `-nan`, whose sign TOML holds and a run can read, and one instant at two offsets; `tomllib` keeps no more than microseconds, so a change below them reads as none), but for the manifest's status, which has only moved forward since: from `prepared` to `running` to `completed` or `failed`, which are final. So neither the falsification criterion nor the results directory nor any setting outside the table changes after a run, and the results directory is a directory below the experiment's directory, not the experiment's directory itself;
- no file the table freezes and no baseline's directory lies in the results directory, or holds it: the runner holds the experiment's files to HEAD except its results directory, where runs write;
- every commit that held the experiment frozen as the runner launches it (listed, past `planned`, its preregistration complete and named by the manifest's digests, its files and baselines as the table freezes them, and a command the runner can build from its manifest and table) holds the same as a run's commit must, since a run could be made there and its record discarded before it was committed: the first committed freeze binds, whichever file it changed alone (the manifest, `config.toml`, the list, the registry, a baseline or a preregistered file). A commit that held less, such as one still holding a placeholder, one holding a frozen file as a symlink, whose target path is all git holds of it, or one whose results directory the runner would refuse, could not launch it and freezes nothing. The gate reads that history as git holds it, without replacement objects, and a history git cannot read fails the gate and refuses every launch rather than reading as empty.

A listed experiment's directory must be a repository path, as the registry names it without a trailing slash, reached through no symlink, since the gate searches the history of such directories only. Its `experiment.toml` and `config.toml` must be regular files, not symlinks: the gate finds a freeze only in a commit that holds them as files, and the runner launches only from one.

The list keeps every experiment it has named at a commit on HEAD's history that the registry holds now or has held at any commit, whether registered before or after it was listed; one taken out of it fails the gate and is refused by the runner, so neither its runs nor its preregistration leave the gate. A listed experiment that was committed frozen, or whose run records were committed, cannot go back to `planned`; it can only be superseded, and it stays bound once superseded: its records stay and its preregistration, manifest and configuration stay as they were, so superseding it erases no outcome.

`scripts/run_experiment.py` refuses to run or prepare a listed experiment until all of this holds for it (`launch_errors`), so none of its outcomes is seen before its preregistration is frozen, and holds the files that decision reads (the list, the registry, the gate, the directories of the entry's baselines and the files its table names, `launch_inputs`) to HEAD before and while the run, as it holds the experiment's own files. It launches only from a commit that holds the experiment frozen as the tree launches it, every frozen input a regular file that commit holds (`launch_commit_errors`, which reads the list and the registry as that commit holds them), so the gate can find the freeze from that commit alone: a file git ignores is in the tree and in no commit. A pilot run outside the runner is not confirmatory evidence, and neither is a run under a runner or gate changed to let it through: the gate judges every commit by its rules as they are now and binds the records the runner keeps, and no rule can know what was run by hand before a freeze. A file or baseline the list names, and every file of a baseline's directory, must be a regular file inside the repository, reached through no symlink: git holds a link as its target's path, so the commit a run names could not show the content frozen through it. A path the list or the table names must not start with `:` or hold `*`, `?` or `[`, which git would read as pathspec magic or a glob rather than as the path, nor pass through git's own directory, `.git` in any case (or, as Windows reads it, with trailing dots or spaces, or as `git~1`), which git refuses to add a path through and where it reports no file as tracked or untracked. It is written as git writes a path, with no `./` step and no doubled or trailing `/`, since git lists a directory's files for `dir/`, and is at most 4096 characters long.

The canonical text (`canonical_text` in `scripts/experiment_records.py`) is `true` or `false`; an integer in decimal; a string between double quotes in which only `\` and `"` are escaped, as `\\` and `\"`, and `/` is not; a list as `[` and its elements joined by `,` and `]`; a table as `{` and its `"key":value` entries in ascending byte order of the keys joined by `,` and `}`; with no whitespace. On this domain it is the JSON Canonicalization Scheme of RFC 8785.

A `must-be-pinned-…` string marks a value still to be chosen and a `must-be-signed-…` string an owner decision still to be taken, which the owner signs by committing the decided value in its place. Either blocks whatever the key's type, and whether or not the list requires the key, as do an empty string, `unconfigured` and `none`, in any case and with any surrounding space, so an owner decision cannot pass as a default. A superseded experiment is not launched: another experiment replaced it, and that one's preregistration counts; one that never left `planned` is not gated, and one that was frozen or ran stays as it was frozen. S003, F003, Q003, R004, M008 and E005 are listed, and all of them are still `planned`.


## Runner

Validate manifests:

```bash
python scripts/run_experiment.py validate
```

Execute a declared experiment entrypoint with an explicitly listed seed:

```bash
python scripts/run_experiment.py run L001 --seed 17 --set iterations=100
python scripts/run_experiment.py run L001 --entrypoint process_entrypoint --seed 17 --set iterations=50
```

The runner never invokes a shell. It tokenizes the versioned `entrypoint` and rejects undeclared seeds, a seed given as a `--set` parameter rather than by `--seed`, unresolved placeholders, and a `--set` naming no placeholder of the command. It fills the placeholders in one pass, so a value is taken as itself, text in it that reads as a placeholder included. Whether a run is a listed experiment's is read from the tree before the watch looks, so the commit the record would name decides (`launch_mode_errors`): the list as that commit holds it names the experiment exactly when the run is listed, and an unlisted run's experiment is one the list has named at no commit on that commit's history, since a commit dropping it from the list in between would otherwise let it run without its frozen values, lock or reservation, and its record be discarded once its outcome was seen. A listed experiment runs only through its `entrypoint`, not another `--entrypoint`, and each placeholder in it besides `<seed>` takes the value its frozen `[preregistration]` table holds under that name: an integer in decimal, a boolean as `true` or `false`, a string as itself. A `--set` may only repeat that value, and a placeholder the table does not hold, or holds as a list, an entrypoint whose first token is empty and so names no program, and a NUL character in the entrypoint or in a value it takes, which no process can be given, are refused, and so is an entrypoint without `<seed>` for a table preregistering more than one seed, which would run one command for every seed while each record named another, and one giving Cargo configuration on its command line (`cargo --config`, also through `rustup run`), a file or a value that can name a rustc wrapper, flags or sources outside the commit, where the repository's own `.cargo/config.toml` is a file of it: a command or a value chosen at launch could be chosen after an outcome was seen and the runs made with the others discarded. A variant of a listed experiment's command is therefore a placeholder its table fixes. A listed experiment runs each seed once: the runner refuses a seed that has a record in the results directory, unless its command failed to launch and so saw no outcome, and the gate refuses two such records of one seed, since a seed run again after its outcome was seen could keep whichever run came out best. A run of a listed experiment holds a lock (a file in git's own directory), so no two of its runs go at once, and reserves its record before the command starts: the reservation (status `started`) is replaced by the whole record once the command ends, and stays as the record that its seed ran when the run dies or goes unrecorded. The runner writes the reservation and then the whole record first to a copy in git's own directory (`.git/ptr-runs/`, under the results directory's path, shared by the clone's worktrees), where the command, which can write in its results directory, does not reach by clearing it; a command that could not start (for want of its program or of a directory for its bytecode cache, or given a NUL character) saw no outcome, so its record, that it failed to launch, is written whatever the tree did meanwhile, and its seed may run; where that record cannot be written, its reservation and copy are removed. A copy git's own directory cannot hold once the command ended (a full disk, say) is removed, and the results directory holds the record alone until it is committed. The runner counts a seed as run when a record in the results directory or a copy says so, and before a launch it puts back from its copy each record of a run at HEAD or a commit on its history that HEAD does not hold and the results directory lost or holds otherwise (`restore_records`), and refuses to launch until it is committed; a copy of a run on another line of history (another branch's, another worktree's) is not put back, since the gate here would refuse its record, and still counts its seed as run: a reservation the command removed or rewrote while its runner was stopped thus comes back, and a lock left by a run that died can be removed by hand without freeing its seed. A record HEAD holds is the gate's to keep as committed. Its launch reads no uncommitted file in the results directory: every earlier record and every output the tools wrote there is committed first, since a command could read one, and only the record the run itself writes is left out of the watch. A copy deleted by hand from git's own directory leaves nothing that clone's runner can see, as a run made by hand or in another clone leaves nothing; a committed record is the gate's to keep. The runner does not sandbox the command, which runs as the runner's own user: a command that deletes the lock and the copies in git's own directory, or signals the runner, defeats them as that user deleting them by hand would. Isolating a run from its own user takes the operating system (another user, a container); what the command does is the frozen harness's committed code, which a review of the freeze reads. A listed experiment's command runs in an environment holding, of the runner's, only `PATH`, `HOME`, `TMPDIR`, `LANG`, `LC_ALL`, `LC_CTYPE`, `CARGO_HOME` and `RUSTUP_HOME` (`COMMAND_ENVIRONMENT`), a relative `PATH` entry made absolute from the repository's root, where the command starts and its program is found,, and `PYTHONNOUSERSITE=1`, so Python reads no package from the user's own site directory: no `PYTHONPATH`, `LD_PRELOAD`, `RUSTC_WRAPPER`, `RUSTUP_TOOLCHAIN` or `RUSTFLAGS` loads code the commit does not hold, and no credential or network setting reaches the command, so its dependencies are fetched before it runs (`cargo fetch`). The runner refuses to run it while Cargo would read configuration from outside the repository, which could set a rustc wrapper, flags or sources: a `.cargo/config.toml` or `.cargo/config` in a directory above the repository, or `config.toml` or `config` in Cargo's home (`CARGO_HOME`, or `.cargo` under `HOME`); what a build needs is set in the repository's own `.cargo/config.toml`, a provenance file. It looks again once the command has ended and records nothing while Cargo would read one; one created and removed again while the command ran is, like any file outside the repository, not seen. Its record names that environment (`environment`), the program the command starts, found on that `PATH` or, for a name with a slash, from the repository's root, through any link, with the SHA-256 of its content (`executable`), and `rustc` and `cargo` as rustup resolves them from the repository's root after its overrides and `rust-toolchain.toml`, or for the toolchain the command names itself, a proxy's first argument (`cargo +stable run`) or the toolchain of `rustup run` (`rustup run stable cargo run`), or as the `PATH` holds them without rustup, with theirs (`toolchain`); a program or tool that is found but cannot be read (a binary that is only executable, say) refuses the run, since one named by its path alone could be replaced between seeds; aggregation and the gate refuse records of one experiment that disagree on any of the three: a program outside the repository, such as a toolchain or an interpreter, is outside what the commit holds, and the record says which one ran. A program the command starts by name in turn (a helper on `PATH`) is found through the environment its seeds share; its content, like the operating system's, is the machine's, which no record binds. The runner writes a unique immutable JSON record containing the Git revision, manifest/lock hashes, the entrypoint and the values its placeholders took (`parameters`), exact argv, duration, exit status, stdout/stderr and launch errors. The record appears whole or not at all, so a write that fails leaves no partial record. Failed executions remain evidence rather than being overwritten.

The Git revision is the commit HEAD was at when the run started. The runner refuses to start from a working tree whose provenance files (the Rust, SQL and protobuf sources, the Cargo and toolchain files, the recording scripts, the experiment's own files apart from its results) HEAD does not hold, counting files only the clone's own ignore rules hide, files that HEAD's `.gitignore` files would show but one HEAD does not hold hides (named by that `.gitignore`), files git is told not to look at, symlinks named as sources, and symlinked directories, nested repositories and submodules where the build reads, such as a `crates/ptr-*` crate linked or cloned in, and writes no record, exiting 2, when HEAD moved or one of those files was written, created or removed while the command ran, even if it was put back (`ProvenanceWatch` in `scripts/experiment_records.py`). `prepare` holds the same files to HEAD before it writes its record. For a listed experiment, those files are every file of the repository, since its command may run or read any of them (a script under `scripts/`, say), and so its archived results (`run.json`, `mutations.json`) are stale, needing a `STALE.toml` marker, once any file of the repository but the tools' outputs in its results and that marker changes after them (`listed_staleness_paths`); and since it could run or read a file git ignores as well, which no commit holds and the watch does not see (a build's output under `target/`, a virtual environment), it runs only from a checkout that holds none (`git clean -ndX` lists them; a fresh worktree holds none), and Cargo in it builds into a fresh directory outside the repository (`CARGO_TARGET_DIR`), from the commit's sources alone; the runner looks again once the command has ended and records nothing while the checkout holds one, which the command could have run or read (one created and removed again while it ran is, as for the watch, not seen). The runner and the gate write no bytecode cache of the modules they import into the tree (`sys.dont_write_bytecode`), so running them as shown above leaves no `__pycache__` directory; other tools may, and `git clean -ndX` shows what they left. The runner leaves out of that check only the files the tools write into the results directory (`run-*.json`, `run.json`, `metrics.json`, `mutations.json`), so every other file there must be one HEAD holds, and it refuses to start while the results directory holds a file git ignores, which most of one is: code or input kept there could change between runs while every record named one commit. The results directory must be a directory below the experiment's directory and outside git's own directory, reached through no symlink, and through no file, which would leave nowhere to write the record once the command had run; it is checked again once the command has run, since the command could have replaced it. A manifest holds no TOML date or time and no NaN: a record holds the manifest as JSON, which has no date or time and writes a NaN as `NaN` whatever its sign, so a date and the string of its text, or `nan` and `-nan`, which a run can tell apart, would be one manifest to aggregation. The runner, `validate` and aggregation refuse either (`unrecordable_keys`), and aggregation compares the manifest with the one a record names as JSON text (`recorded_text`), where `1`, `1.0` and `true` are three values, and so are `0.0` and `-0.0`, and `inf` and `-inf`. The runner builds the command and the record from the manifest it read first, and refuses when the tree the watch then holds has another; and git runs without the environment's `GIT_*` variables, which could point it at another work tree or change how it reads pathspecs, and without a file system monitor or a hook the clone's own configuration names, which could answer for the tree or run while git refreshes its index, and it tells names apart by case (`core.ignoreCase=false`), as the file system does where it does, so no `src/Helper.py` is taken for a tracked `src/helper.py`. The watch also reads each tracked file's bytes from disk and compares them with HEAD's blob, and its executable bit with HEAD's mode (`content_changes`), so no clean filter the clone's own attributes name, no monitor and no stat cache it trusts has git report a rewritten source as unchanged; a copy that differs from a blob holding no carriage return only in CRLF line endings, as a converting checkout writes one, holds HEAD's content. Python in the command keeps its bytecode cache in a fresh directory (`PYTHONPYCACHEPREFIX`), so no `__pycache__` entry the tree holds, which git ignores, runs in place of a tracked source.

Every experiment's `aggregate.py` (L001, L003 and L004 today) publishes `results/run.json` and `results/metrics.json` as one aggregate: `run.json` names the SHA-256 of the `metrics.json` written with it, and an interrupted publish leaves no `run.json` rather than the previous one beside new metrics. The L003 and L004 aggregators refuse to aggregate in a checkout holding provenance files HEAD does not hold, and `scripts/check_research_gates.py` fails a completed experiment whose `run.json` is not one aggregate with the `metrics.json` and `mutations.json` beside it (`publish_aggregate` and `aggregate_errors` in `scripts/experiment_records.py`). A current `run.json` must name that SHA-256. One aggregated before `run.json` named it, as the archived L003 and L004 results of ad2f8d1 were, passes only while it is stale and while it and the `metrics.json` beside it are the pair the last commit that changed `run.json` holds.
