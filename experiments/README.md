# PTR Experiments

Every experiment has an ID, hypothesis, baseline, seeds, metrics, falsification criterion and immutable result directory. `experiments/registry.toml` registers each ID once, in one directory: `run_experiment.py validate` and the research gate refuse an ID registered twice, which the gate would check in one place and the runner could launch in neither.

Categories:
- `model/`
- `semdb/`
- `runtime/`
- `lifecycle/`
- `retrieval/`
- `feedback/`
- `system/`

Do not silently rewrite failed results. Supersede them with a new experiment/version and record the decision in `research/decisions/`.

## Preregistration

An experiment listed in `preregistration.toml` leaves `planned` only with a frozen preregistration. Once its status is `prepared`, `running`, `completed` or `failed`, `scripts/check_research_gates.py` fails CI unless:

- its manifest names its `entrypoint`, since the manifest is frozen from the first commit past `planned` and one named later could never be named, and the runner can build its command: it splits as a command, and each placeholder in it but `<seed>` is a key of the `[preregistration]` table holding an integer, a string or a boolean, the value the runner fills it with, it takes `<seed>` when the table preregisters more than one seed, and it gives Cargo no configuration on its command line (`--config`), as the runner fills its placeholders, since a freeze no run can use cannot be repaired;
- its `config.toml` holds a `[preregistration]` table with every key the list requires, each a pinned value of its declared type (`int`, `str`, `bool`, a non-empty `int-list` or `str-list`, or `file`), and no other key of the table holds a placeholder either;
- every value of that table is a boolean, an integer of magnitude at most 2^53 − 1, a string of printable ASCII or a list of only such integers or only such strings, and every key is printable ASCII, so that its canonical text has one spelling whoever writes it; `experiment.toml`'s `preregistration_sha256` is the SHA-256 of that text;
- a `file` key names a file in the repository, and the table's `<key>_sha256` is the SHA-256 of that file (`preregistered_bytes_digest`: every file is digested byte for byte, so its line endings are content, and a checkout that converts them, as `core.autocrlf` does, holds another file, whose digest differs from the table's), so the file's content is frozen with the table, not only its path. Since that digest holds the content alone, the file is not executable (mode `100644`, in the index and in every commit), as the executable bit changes what a command does with it. The repository's `.gitattributes` pins its files to LF line endings (`* text=auto eol=lf`), so a clone checks out the bytes that were committed whatever `core.autocrlf` says, and no two committed versions that a command would read apart share a digest;
- the table's `seeds`, which every entry of the list must require as an `int-list`, names the manifest's seeds, integer for integer, each once, so no seed can be added after an outcome is seen and none counts twice in an aggregate;
- every baseline the list names is pinned at each key the list names for it, its status is pinned and not `blocked-*`, and the table's `baseline_<name>_sha256` is the digest of every file in the baseline's directory, whose files are digested as they are, byte for byte (line endings are content, and `.gitattributes` pins text files to LF): the canonical text of the table mapping each file's path within the directory to its git mode and its SHA-256 (read as a `file` key's is), written `<mode> <sha256>` (`100644`, or `100755` for an executable file), over the files git tracks or would track there, so every setting of the baseline, not only the keys that must be pinned, and the implementation beside its configuration, down to which of its files are executable, are frozen with the table. The directory holds no file its `.gitignore` files ignore, such as a `__pycache__` entry, which an interpreter could run in place of a tracked file and git does not hold, and every file in it is named as a repository path (below), a name that is not UTF-8 being none; a commit whose baseline directory held another, such as `helper[old].py`, could not launch the experiment and froze nothing, whether or not its table named a digest of the baseline, so renaming the file is a repair, not a rewrite;
- `experiment.toml`'s `preregistration_rules_sha256` is the SHA-256 of the canonical text of the experiment's entry in `preregistration.toml`, so its types and baselines are frozen with the table;
- every run record (`run-*.json`, whose manifest `run_experiment.py` records) and aggregate (`run.json`) the experiment has committed in a results directory it has had (`results`, or a `results_dir` a committed manifest named) in any directory the registry has given it, whatever its `results_dir` is now, and those in its results directory (a file of that name elsewhere, such as a test's fixture, is none), name those two digests and the commit they ran at (`git_sha`), and that commit is on HEAD's history, where the registry placed the experiment in the directory it places it in now, and holds the same `[preregistration]` table, manifest digests, list entry, files and baselines; a run record also names the SHA-256 of `experiment.toml` at that commit (`manifest_sha256`) and has held the same content in every commit on every side of every merge since it was committed, which the working tree holds too, its bytes read from disk against HEAD's blob (a record the index marks skip-worktree or assume-unchanged, which git diff and status take as HEAD's whatever it holds, included), an aggregate, which an aggregator may write again, holds to this in every version it was committed in, each version a regular file, each once committed is at HEAD where it was committed (one deleted and put back as it was, as a revert of its revert puts it back, is the record committed: while it is missing the gate fails and the runner launches nothing), no two run records are of one seed but for a command that failed to launch, since a seed run again after its outcome was seen could keep whichever run came out best, and the run records all name one program, one Rust toolchain and one environment (`executable`, `toolchain`, `environment`), which lie outside the commit and a replacement between seeds would leave unnamed (a program the command starts by name is found through the environment's `PATH`), and ran one tree: the repository at each run's commit is the first run's but for the seed records (`run-*.json`) of the results directory, since the command may run or read any file of it, an aggregate (`run.json`, `metrics.json`) or mutation evidence (`mutations.json`) committed between seeds included, which the tools write once the seeds have run (a script under `scripts/` changed and committed between seeds would leave records naming commits of different code; `listed_record_paths`, which a listed experiment's aggregator passes to `source_revision` too, with `listed_staleness_paths` as the paths it compares its checkout by and `listed_experiment`, since the tools' outputs, the stale marker and what completing the experiment changes are committed after the seeds), and each is a regular file reached through no symlink. A preregistration rewritten after its runs thus fails even when the manifest and the records are rewritten to match, short of rewriting history. An aggregator of a listed experiment writes `preregistration_sha256`, `preregistration_rules_sha256` and `git_sha` into `run.json`;
- the manifest and `config.toml` at every such commit are the ones now, value for value and of one type (`1`, `1.0` and `true` are three values, and so are `0.0` and `-0.0`, and `nan` and `-nan`, whose sign TOML holds and a run can read, and one instant at two offsets; `tomllib` keeps no more than microseconds, so a change below them reads as none), but for the manifest's status, which has only moved forward since: from `prepared` to `running` to `completed` or `failed`, which are final, or to `superseded`, which is final once the experiment was frozen; and no commit that descends from a freeze, on any side of any merge, holds it at an earlier status, whether or not a later commit puts it right again (`status_regressions`), since a manifest that ran and was prepared again between two freezes is one whose runs could be chosen. So neither the falsification criterion nor the results directory nor any setting outside the table changes after a run, and the results directory is a directory below the experiment's directory, not the experiment's directory itself;
- no file the table freezes and no baseline's directory lies in the results directory, or holds it: the runner holds the experiment's files to HEAD except its results directory, where runs write;
- every commit that held the experiment frozen as the runner launches it (listed, past `planned`, its preregistration complete and named by the manifest's digests, its files and baselines as the table freezes them, and a command the runner can build from its manifest and table) holds the same as a run's commit must, since a run could be made there and its record discarded before it was committed: the first committed freeze binds, whichever file it changed alone (the manifest, `config.toml`, the list, the registry, a baseline or a preregistered file). A commit that held less, such as one still holding a placeholder, one holding a frozen file as a symlink, whose target path is all git holds of it, or one whose results directory the runner would refuse, could not launch it and freezes nothing. The gate reads that history as git holds it, without replacement objects, and a history git cannot read fails the gate and refuses every launch rather than reading as empty.

A listed experiment's directory must be a repository path, as the registry names it without a trailing slash, reached through no symlink, since the gate searches the history of such directories only. Its `experiment.toml` and `config.toml` must be regular files, not symlinks: the gate finds a freeze only in a commit that holds them as files, and the runner launches only from one.

The list keeps every experiment it has named at a commit on HEAD's history that the registry holds now or has held at any commit, whether registered before or after it was listed; one taken out of it fails the gate and is refused by the runner, so neither its runs nor its preregistration leave the gate. A listed experiment that was committed frozen, or whose run records were committed, cannot go back to `planned`; it can only be superseded, and it stays bound once superseded: its records stay and its preregistration, manifest and configuration stay as they were, so superseding it erases no outcome.

`scripts/run_experiment.py` refuses to run or prepare a listed experiment until all of this holds for it (`launch_errors`), so none of its outcomes is seen before its preregistration is frozen, and holds the files that decision reads (the list, the registry, the gate, the directories of the entry's baselines and the files its table names, `launch_inputs`) to HEAD before and while the run, as it holds the experiment's own files. It launches only from a commit that holds the experiment frozen as the tree launches it, every frozen input a regular file that commit holds (`launch_commit_errors`, which reads the list and the registry as that commit holds them), so the gate can find the freeze from that commit alone: a file git ignores is in the tree and in no commit. A pilot run outside the runner is not confirmatory evidence, and neither is a run under a runner or gate changed to let it through: the gate judges every commit by its rules as they are now and binds the records the runner keeps, and no rule can know what was run by hand before a freeze. A file or baseline the list names, and every file of a baseline's directory, must be a regular file inside the repository, reached through no symlink: git holds a link as its target's path, so the commit a run names could not show the content frozen through it. A path the list or the table names must not start with `:` or hold `*`, `?` or `[`, which git would read as pathspec magic or a glob rather than as the path, nor pass through git's own directory, `.git` in any case (or, as Windows reads it, with trailing dots or spaces, or as `git~1`), which git refuses to add a path through and where it reports no file as tracked or untracked. Nor may it hold a name Windows reads as a step it is not written as (`.` or `..` with trailing dots or spaces, a name of dots and spaces only, or one of these with an NTFS stream: `.. `, `...`, `..:x`), which would climb out of its directory or name it again as another entry, nor begin with a drive letter and a colon (`C:x`, `C:/x`), which Windows reads as a path on that drive; a name that only starts or ends with dots beside other characters (`..x`, `a..`) is a name of its own. The same holds for a `results_dir` and for a path a listed Cargo command gives (`--manifest-path`, `--lockfile-path`). It is written as git writes a path, with no `./` step and no doubled or trailing `/`, since git lists a directory's files for `dir/`, and is at most 4096 characters long.

The canonical text (`canonical_text` in `scripts/experiment_records.py`) is `true` or `false`; an integer in decimal; a string between double quotes in which only `\` and `"` are escaped, as `\\` and `\"`, and `/` is not; a list as `[` and its elements joined by `,` and `]`; a table as `{` and its `"key":value` entries in ascending byte order of the keys joined by `,` and `}`; with no whitespace. On this domain it is the JSON Canonicalization Scheme of RFC 8785.

A `must-be-pinned-…` string marks a value still to be chosen and a `must-be-signed-…` string an owner decision still to be taken, which the owner signs by committing the decided value in its place. Either blocks whatever the key's type, and whether or not the list requires the key, as do an empty string, `unconfigured` and `none`, in any case and with any surrounding space, so an owner decision cannot pass as a default. A superseded experiment is not launched: another experiment replaced it, and that one's preregistration counts; one that never left `planned` is not gated, and one that was frozen or ran stays as it was frozen. S003, F003, Q003, R004, M008 and E005 are listed, and all of them are still `planned`.


## Runner

Validate manifests:

```bash
python scripts/run_experiment.py validate
```

Execute a declared experiment entrypoint with an explicitly listed seed:

```bash
python scripts/run_experiment.py run L001 --seed 17 --set iterations=100
python scripts/run_experiment.py run L001 --entrypoint process_entrypoint --seed 17 --set iterations=50
```

The runner never invokes a shell. It tokenizes the versioned `entrypoint` and rejects undeclared seeds, a seed given as a `--set` parameter rather than by `--seed`, unresolved placeholders, and a `--set` naming no placeholder of the command. It fills the placeholders in one pass, so a value is taken as itself, text in it that reads as a placeholder included. What decides a launch is read from the tree before the watch looks, so it is decided again from the tree the watch holds to HEAD (`launch_errors`), and the experiment must be where the registry placed it when the launch read its values; and whether a run is a listed experiment's, the commit the record would name decides (`launch_mode_errors`): the list as that commit holds it names the experiment exactly when the run is listed, and an unlisted run's experiment is one the list has named at no commit on that commit's history, since a commit dropping it from the list in between would otherwise let it run without its frozen values, lock or reservation, and its record be discarded once its outcome was seen. A listed experiment runs only through its `entrypoint`, not another `--entrypoint`, and each placeholder in it besides `<seed>` takes the value its frozen `[preregistration]` table holds under that name: an integer in decimal, a boolean as `true` or `false`, a string as itself. A `--set` may only repeat that value, and a placeholder the table does not hold, or holds as a list, an entrypoint whose first token is empty and so names no program, and a NUL character in the entrypoint or in a value it takes, which no process can be given, are refused, and so is an entrypoint without `<seed>` for a table preregistering more than one seed, which would run one command for every seed while each record named another, and one running Cargo otherwise than as one of its built-in commands `bench`, `build`, `check`, `run` or `test`, first after at most a rustup `+<toolchain>` (`cargo_command_errors`), also through `rustup run`, and however a platform spells the program (`cargo.exe`, `C:\Rust\CARGO.EXE`): Cargo lets no alias of its configuration shadow a built-in command and runs no program of another name for one, so what follows is read as written, where an alias, an option before the command (`--`, `-C`, `-Zscript`) or an external command (`cargo clippy` runs `cargo-clippy` from the `PATH`) would have Cargo read it otherwise or run a program no record names. Up to a `--`, past which they are the built program's, its arguments give Cargo no configuration (`--config`: a file or value can name a rustc wrapper, flags or sources outside the commit), no directory to run in (`-C`, in any spelling), no target directory (`--target-dir`), which could hold a build made outside the commit, where the runner builds a listed run into a fresh one, and no manifest, lockfile or target specification file outside what the repository's watch reads (`--manifest-path`, `--lockfile-path`, `--target custom.json`: an absolute path, one climbing above the root, or one through git's own directory, which no scan of the tree lists, however a platform names it: `.git` in any case, and as Windows reads it, `.git.`, `.git `, `git~1` or `.git::$INDEX_ALLOCATION`), or one with a colon in a component (`targets/base:evil.json`, which Windows reads as an NTFS stream of `base`, a file no scan of the tree lists, and every platform refuses it alike), whose sources no watch or record binds; Cargo takes a long option only by its full name. And the gate refuses one whose Cargo configuration in the repository, `.cargo/config` and `.cargo/config.toml` at the root, which Cargo started from the root reads, by the command or by a program it runs, does not parse or sets anything but `[alias]`, `[cargo-new]`, `[future-incompat-report]`, `[http]`, `[net]` and `[term]` (`cargo_configuration_errors`), since the rest can name a program Cargo runs (a compiler or its wrapper, `rustdoc`, a linker, or a runner the built program is started through, which Cargo runs in its place), a source or file it builds from (a path override, a patch, a source replacement, an included configuration, a target), flags it builds with, or variables it sets for what it runs (`[env]`, where `LD_PRELOAD` would load a library outside the environment the runner pins), none of which the record binds, where it names the `rustc` rustup or the `PATH` resolves (Cargo started from another directory, by a program the command runs, reads that directory's configuration too, which the gate cannot see): a command or a value chosen at launch could be chosen after an outcome was seen and the runs made with the others discarded. A variant of a listed experiment's command is therefore a placeholder its table fixes. Before a listed experiment's seed runs, the runner compares it with the seeds its results already hold, as the gate will: a seed that would run another program, toolchain or environment, or another repository but for their seed records, is refused before it runs rather than spent. A listed experiment runs each seed once: the runner refuses a seed that has a record in the results directory, unless its command failed to launch and so saw no outcome, and the gate refuses two such records of one seed, since a seed run again after its outcome was seen could keep whichever run came out best. A run of a listed experiment holds a lock (a file in git's own directory, named by the experiment's id with every character a file name could not hold percent-encoded, and a long id by its beginning and its SHA-256, so every id names a file a file system holds), so no two of its runs go at once, and so does its `prepare`, whose record a running seed's watch would otherwise see, leaving that run unrecorded and its seed spent, and reserves its record before the command starts: the reservation (status `started`) is replaced by the whole record once the command ends, and stays as the record that its seed ran when the run dies or goes unrecorded. The runner writes the reservation and then the whole record first to a copy in git's own directory (`.git/ptr-runs/`, under the results directory's path, shared by the clone's worktrees), where the command, which can write in its results directory, does not reach by clearing it; a command that could not start (for want of its program or of a directory for its bytecode cache, or given a NUL character) saw no outcome, so its record, that it failed to launch, is written whatever the tree did meanwhile, and its seed may run; where that record cannot be written, its reservation and copy are removed. A copy git's own directory cannot hold once the command ended (a full disk, say) is removed, and the results directory holds the record alone until it is committed. The runner counts a seed as run when a record in the results directory or a copy says so, and before a launch it puts back from its copy each record of a run at HEAD or a commit on its history that HEAD does not hold and the results directory lost or holds otherwise (`restore_records`), and refuses to launch until it is committed; a copy of a run on another line of history (another branch's, another worktree's) is not put back, since the gate here would refuse its record, and still counts its seed as run: a reservation the command removed or rewrote while its runner was stopped thus comes back, and a lock left by a run that died can be removed by hand without freeing its seed. A record HEAD holds is the gate's to keep as committed. Its launch reads no uncommitted file in the results directory: every earlier record and every output the tools wrote there is committed first, since a command could read one, and only the record the run itself writes is left out of the watch, which stamps that record (the reservation) once the runner has written it, so an edit to it that is put back, or a copy of it put in its place, while the command runs leaves the run unrecorded (`stamp_reserved`). A copy deleted by hand from git's own directory leaves nothing that clone's runner can see, as a run made by hand or in another clone leaves nothing; a committed record is the gate's to keep. The runner does not sandbox the command, which runs as the runner's own user: a command that deletes the lock and the copies in git's own directory, or signals the runner, defeats them as that user deleting them by hand would. Isolating a run from its own user takes the operating system (another user, a container); what the command does is the frozen harness's committed code, which a review of the freeze reads. A listed experiment's command runs, where rustup resolves its toolchain, with `RUSTUP_TOOLCHAIN` naming the directory of the toolchain rustup resolved for the launch, which rustup takes as the toolchain itself whether it installed it or a path names it, so an override changed while the command runs, and put back, selects no other toolchain for the proxies it starts; its environment holds, of the runner's, only `PATH`, `HOME`, `TMPDIR`, `LANG`, `LC_ALL`, `LC_CTYPE`, `CARGO_HOME` and `RUSTUP_HOME` (`COMMAND_ENVIRONMENT`), none of which names a directory by a relative path (a relative or empty `PATH` entry, a relative `HOME`, `TMPDIR`, `CARGO_HOME` or `RUSTUP_HOME`), which each program would resolve from wherever it starts, so the run is refused while one does (`relative_directories`),, and `PYTHONNOUSERSITE=1`, so Python reads no package from the user's own site directory, and `PYTHONHASHSEED=0`, so Python hashes strings the same way in every run and an order that follows hashing (a set's) is the same for every seed rather than one each process draws: no `PYTHONPATH`, `LD_PRELOAD`, `RUSTC_WRAPPER`, `RUSTUP_TOOLCHAIN` or `RUSTFLAGS` loads code the commit does not hold, and no credential or network setting reaches the command, so its dependencies are fetched before it runs (`cargo fetch`). The runner refuses to run it while Cargo would read configuration from outside the repository, which could set a rustc wrapper, flags or sources: a `.cargo/config.toml` or `.cargo/config` in a directory above the repository, or `config.toml` or `config` in Cargo's home (`CARGO_HOME`, or `.cargo` under `HOME`); what a build needs is set in the repository's own `.cargo/config.toml`, a provenance file. It looks again once the command has ended and records nothing while Cargo would read one; one created and removed again while the command ran is, like any file outside the repository, not seen. Its record names that environment (`environment`), the program the command starts, found on that `PATH` or, for a name with a slash, from the repository's root, through any link, with the SHA-256 of its content (`executable`), and `rustc` and `cargo` as rustup resolves them from the repository's root after its overrides and `rust-toolchain.toml`, or for the toolchain the command names itself, a proxy's first argument (`cargo +stable run`) or the toolchain of `rustup run` (`rustup run stable cargo run`), each program read as a platform runs it (`rustup.exe` is rustup), or as the `PATH` holds them where they are not rustup's proxies (without rustup, or a standalone Cargo before its proxies), with theirs (`toolchain`); a program or tool that is found but cannot be read (a binary that is only executable, say), or that changes while it is read, refuses the run, since one named by its path alone could be replaced between seeds. The command starts its program by the name the launch found it by (a name on `PATH` joined to its directory, one with a slash as it stands), so a script reads the name it was started by (`$0`) as it would anywhere and a program put earlier on `PATH` once the launch had read the named one does not run in its place; a program the launch found none of is not started at all, as the process would look the name up again: the command fails to launch, and its seed may run once the program is there. The runner records nothing when a file whose digest the record names, or a link on the way to it from the name the command starts, changed between the launch reading it and the command's end: every write or replacement of a file or link moves its stamp (its inode, size, modification and status-change times), which ordinary tools cannot set back, so a program replaced for the run and put back afterwards is seen, as the watch sees a source edited and put back. Aggregation and the gate refuse records of one experiment that disagree on any of the three: a program outside the repository, such as a toolchain or an interpreter, is outside what the commit holds, and the record says which one ran. A program the command starts by name in turn (a helper on `PATH`) is found through the environment its seeds share; its content, like the operating system's, is the machine's, which no record binds, and so are the libraries and interpreter packages a program loads from outside the repository. Binding that closure takes a hermetic environment (a container image named by its digest, say), which the runner does not provide: hashing every program on `PATH` its user could replace would read gigabytes per run (as root, everything) and still leave the libraries and packages unbound. The stamp binds a named program's file, not the path to it, so a directory above it renamed away and put back while the command ran, which leaves the file's stamp as it was, is the machine's too. The runner writes a unique immutable JSON record containing the Git revision, manifest/lock hashes, the entrypoint and the values its placeholders took (`parameters`), exact argv, duration, exit status, stdout/stderr and launch errors. The record appears whole or not at all, so a write that fails leaves no partial record. Failed executions remain evidence rather than being overwritten.

The Git revision is the commit HEAD was at when the run started. The runner refuses to start from a working tree whose provenance files (the Rust, SQL and protobuf sources, the Cargo and toolchain files, the recording scripts, the experiment's own files apart from its results) HEAD does not hold, counting files only the clone's own ignore rules hide, files that HEAD's `.gitignore` files would show but one HEAD does not hold hides (named by that `.gitignore`), files git is told not to look at, symlinks named as sources, and symlinked directories, nested repositories and submodules where the build reads, such as a `crates/ptr-*` crate linked or cloned in, and writes no record, exiting 2, when HEAD moved or one of those files was written, created or removed while the command ran, even if it was put back (`ProvenanceWatch` in `scripts/experiment_records.py`). A listed run also stamps, right before its command starts, its own reservation, which the watch leaves out and the command can read, and the repository's root and every directory holding a watched file; it writes no record when the reservation was written to, replaced or removed, even if its bytes were put back, nor when one of the directories was renamed away and put back, or had an entry added or removed, which the stamps of the files inside it do not show (the directories above the repository are not stamped). `prepare` holds the same files to HEAD before it writes its record. For a listed experiment, those files are every file of the repository, since its command may run or read any of them (a script under `scripts/`, say), and every path git does not look into is one, a submodule, nested repository or linked directory at its root included, and so its archived results (`run.json`, `mutations.json`) are stale, needing a `STALE.toml` marker, once any file of the repository but the tools' outputs in its results and that marker changes after them (`listed_staleness_paths`), the list of preregistrations included; its manifest and the registry change after them only in the status completing it moves, each on its line, and any other change to them, another experiment's entry or a comment, is one too (`completion_changes`), since its command may read either whole; and since it could run or read a file git ignores as well, which no commit holds and the watch does not see (a build's output under `target/`, a virtual environment), it runs only from a checkout that holds none (`git clean -ndX` lists them; a fresh worktree holds none), nor an empty directory, whose presence a command can test, or an entry named as git's own directory below the root (`.git` in any case, and as Windows reads it, `.git.` or `git~1`), or at the root under any name but `.git`, which git never looks into, or a file that is neither a regular file nor a symlink (a FIFO, a socket, a device), which a command can test for or read what another process writes into, or a directory the walk cannot list (one without search permission), which a command can see though git lists nothing of it, none of which git lists (`unlisted_entries`), nor a file name that is not UTF-8, which git prints as bytes no check can read (git's output is read as UTF-8 whatever the locale, whose encoding could read such bytes as text, or a UTF-8 name as another name, and as it is printed, a carriage return in a name included; a comparison of two commits, or a walk of the history after results, reads such a name by its bytes, a difference like any other), and Cargo in it builds into a fresh directory outside the repository (`CARGO_TARGET_DIR`), from the commit's sources alone: one of the experiment's name in its temporary directory (`TMPDIR`, `ptr-run-<id>`), beside Python's bytecode cache (`PYTHONPYCACHEPREFIX`), made for each run only if absent and removed after it, so its path, which the command can read, is the same for every seed and the record's environment names it; one left by a run that died refuses the run until it is removed by hand; the runner looks again once the command has ended and records nothing while the checkout holds one, or an entry git does not list, which the command could have run or read (one created and removed again while it ran is not seen there, though the watch sees it when it was made in a directory holding a watched file). So a listed experiment's command writes nothing git ignores into the repository: its logs, checkpoints and caches go outside it (`TMPDIR`, say; pytest with `-p no:cacheprovider`), and its record is one no rule of the repository or the clone ignores, which the runner checks before it starts.
