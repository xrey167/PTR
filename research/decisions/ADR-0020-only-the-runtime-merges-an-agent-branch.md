# ADR-0020 — Only the Runtime Merges an Agent Branch

## Status
Accepted for the prototype with roadmap item T1-2 (`ptr-runtime`, `ptr-ledger`, `ptr-state`, `ptr-branch`, `ptr-pg`). It amends ADR-0017, whose Decision made committing a certified plan through verification the caller's obligation. S003 measures the path this ADR fixes, and the throughput and lost-update claims of ADR-0017 stay gated on it.

## Decision
A sealed branch reaches semantic state only through `PtrRuntime::merge_branch(sealed, authority)`. In one call the runtime certifies the branch against its own published state with its own `generation_validity`, refuses a branch id already merged in this history (`BranchAlreadyMerged`), refuses a plan that writes a key reserved to ingress or would evict one, and hands every verifier of the host-installed `SemanticGrant` the change: the state before and after, the exact delta, the affected keys, and as its origin the sealed branch, the plan and whether it was rebased. The change is admitted only if every verifier passes, the weakest level any of them reports meets the grant's requirement, and no report has a hard finding. An admitted change commits under one of two authorities: `Triage`, under the grant's merge policy and a calibration seed the grant never records, returns or prints, where only `AutoPropose` commits; or `Reviewed`, where a reviewer the grant lists approved exactly that plan digest. Nothing else commits: a change the verifiers do not admit is held whatever authorizes it, an escalated or calibration-slice branch is held with its triage, and a no-op appends nothing and leaves the id unmerged. A merge appends one `SemanticDeltaCommitted` record whose origin names the branch, its author, the sealed branch's digest (`SealedBranch::seal_digest`), the plan digest, the dependency digest, the rebased keys, the verifiers with their weakest level and soft findings, and the authority. Every refusal and hold comes before that append and leaves the runtime unfenced, a record too large to frame (`MAX_RECORD_BYTES`) or carrying more rebased keys than a delta holds (`MAX_DELTA_ITEMS`) included. `MergePlan` is a read-only what-if (`preview_merge`, `certify`); `apply_certified_semantic_delta` is removed.

Every other semantic write has an origin too. Ingress writes exactly the shape its origin fixes, with no grant verifier: `request:<id>:raw` for a request, and one Pod output with its dependency on the raw request once the Pod's verifier passed with no hard finding. A host write (`apply_verified_semantic_delta(expected, delta, principal)`) is admitted by the same grant, only if the grant enables host writes, and is recorded under its principal; a plan's delta written that way is a host write, never a merge. `PtrRuntime::commit` refuses every semantic record. The grant is installed once per runtime and is not history.

The ledger carries the origin: `Legacy` keeps tag 8 byte for byte, and every attributed origin is the new tag 12, with bounded attestations the decoder and every append path check alike (`check_encodable`). Every path that rebuilds a runtime from its history (replay, `open_durable`, `open_durable_at`, a recovery snapshot, a compacted restore) validates every origin with the rules the writers run before they append: R1, a record without an origin only before the first attributed one (the `semdb:attested` marker); R2, ingress records only in their exact shapes; R3, host writes and merges with valid provenance text and attestations, touching no ingress key; R4, a merge with no dependency entry, rebased keys neither removed nor reserved, the plan digest recomputed from the record's own parts (`merge_plan_digest`), and at most one merge per branch id. The merged branches (`branch-merge:<len>:<id>`) and the marker are materialized state, so they survive compaction; the compacted snapshot is `PTRCS004` with lifecycle section `PTRLC002`, and `PTRCS003` with `PTRLC001` is still read as a history without attributed records. This departs from the rule that a legacy log stays readable as it is: a history with an attributed record no longer accepts an unattributed one after it, which is safe because a build from before attributed records stops at tag 12 and at the new snapshot magic instead of extending such a history.

The PostgreSQL work schema follows. `record_outcome` writes a merged outcome only when its projection holds that branch's merge at exactly the claimed index, and under a branch seal key the host holds outside PostgreSQL, `store_branch` tags each branch it stores and `load_branch` returns only a branch whose rows carry the key's tag of exactly what they rebuild into. Tags are a table of their own, and a branch may carry one per key, so a branch stored without one is tagged in place (`seal_stored_branch`) once the host vouches for its rows, and a key is rotated by tagging under the new one.

Decided with it:
- O1: the compacted snapshot is `PTRCS004`/`PTRLC002`, and `PTRCS003`/`PTRLC001` is still read as pre-attestation, refusing a `PTRLC001` section that holds the marker or a merge key and any mismatched pair.
- O2: `apply_certified_semantic_delta`, `StaleReliance` and `StaleTarget` were kept as a grant-verified host write while the origin rules landed, then removed with `merge_branch`, which refuses a stale reliance through certification (`LifecycleChanged`).
- O3: the merged-outcome check is `record_outcome`'s, not a work-schema trigger's, since a trigger would read a projection schema a rebuild drops; a merged row written around it is not checked.
- O4: a branch without a seal tag, loaded under a key, is its own refusal (`BranchWithoutSealTag`), distinct from a tag that does not verify (`BranchSealMismatch`).
- O5: a branch id or author that is not provenance text is refused at merge, not when the branch is sealed or stored.
- O6: L004 writes attributed records before L003 and L004 are rerun, so the PostgreSQL, Turso and event projections of the marker and the merge keys are compared too.
- O7: L003 and L004 are rerun once, after the last change to provenance, with the preregistration gate merged first.

## Consequences
A certified plan can no longer be committed without verification, altered after certification, bound to another host by a revision number, merged after a relied-on generation was revoked, or merged twice; a copy of its delta can be written only as an attributed host write, never as a merge. Verification still outranks triage and review (INVARIANT 11): triage and review can only hold a change the verifiers admit. The ledger says why every semantic write was allowed, but what it records is the runtime's own claim, at the trust level of `EffectAttempted.verification`. Writers below the runtime (`Ledger::append`, `FileLedger::append_durable`, `AcknowledgedLedger::append_acknowledged`, `RaftEngineLedger::append_durable`, `RaftNode::propose`, through which `ptr-cluster` members propose, and `SingleNodeRaftConsensus::propose`) can still write a well-formed record the rules accept, and a fresh log whose first records are forged tag-8 records is accepted as a legacy prefix; replay cannot run the verifiers again, only check what is deterministic about a record. "Host-installed" means chosen once by whoever builds the runtime, not a sandbox against code holding `&mut PtrRuntime`. The author, the host principal and the reviewer are recorded as given until principals are authenticated. The calibration seed is never recorded or returned, because a caller who knew it could choose branch ids outside the calibration slice. Approvals bind to a plan digest that includes the certified revision, so any commit voids a pending review. Tag-12 records and `PTRCS004` snapshots are unreadable by older binaries, so readers upgrade first. The merged set grows with every merge and shares the compacted snapshot's item bound with effect records until branch leases let entries expire. A seal tag binds stored rows to a holder of the key, not to the author, and a substrate without a key checks none.
